# ADR-0007: 動作確認は Chrome (macOS) と iPhone の 2 環境で行う

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連**: ADR-0001, ADR-0006
- **関連 Issue**: #49, #2, #6, #26, #27, #40, #43, #46

## コンテキスト

ADR-0006 で対応環境を「デスクトップ Chrome + iOS Safari + Android Chrome」と定めたが、
**実際にどの環境で動作確認を行うか**という手順は決めていなかった。

その後、開発者の利用環境が判明した。

- 開発機: **Mac**
- 実機確認: **iPhone**
- **macOS の Safari は日常的に使用していない**
- Android 実機は手元にない

当初、Chrome (macOS) → Safari (macOS) → iPhone の 3 段階での確認を提案したが、
開発者から「Safari は基本的に使用していないので確認しなくてよいのでは」との提起があった。

## ADR-0006 との関係

ADR-0006 の**対象環境の決定は変更しない**。Chrome / iOS / Android を対応対象とする点はそのまま有効。

本 ADR が更新するのは**確認手順**のみである。
ADR-0006 は「動作確認が 3 環境必要になる」と記していたが、
Android 実機を持たないことが判明したため、確認は 2 環境に絞る。
確認手順に関しては**本 ADR が ADR-0006 に優先する**。

## 決定

**動作確認は Chrome (macOS) と iPhone の 2 環境で行う。**

| 環境 | 位置づけ | 確認 |
| --- | --- | --- |
| Chrome (macOS) | 開発とデバッグの主環境 | 常時 |
| iPhone (ホーム画面に追加した状態) | 実利用の主環境。**WebKit の唯一の検証点** | 早期かつ継続的に |
| Safari (macOS) | 確認対象外 | 行わない |
| Android Chrome | 対応するが実機がないため未検証 | 行わない |

## 重要な区別: 「Safari を使わない」と「WebKit を避けられる」は別

macOS の Safari を確認対象から外す判断は妥当だが、
**iPhone 上のブラウザは Safari (WebKit) である**という事実は変わらない。

iOS では、実質的にすべてのブラウザが WebKit エンジンを使用している。
iPhone に Chrome や Firefox を入れても、描画と JavaScript の実行は WebKit が行う。

> EU の DMA や日本のスマホソフトウェア競争促進法により代替エンジンを認める動きがあるが、
> 主要ブラウザが iOS で独自エンジンを実際に採用した例は確認できていない。
> 設計上は WebKit を前提とするのが安全である。

したがって、**ADR-0001 に記録した iOS Safari の制約はすべてそのまま有効**である。

- 7 日間の無操作でストレージ削除（ホーム画面追加で回避）
- `navigator.vibrate()` 非対応
- 音声の自動再生制限

**「Safari を使わない」は確認手順の話であり、対象環境が変わったわけではない。**
この区別を取り違えると、iOS 固有の制約を軽視した実装につながる。

## 検討した選択肢

### 案 A: Chrome → Safari (macOS) → iPhone の 3 段階 — 却下

- 利点:
  - macOS Safari は iPhone と同じ WebKit のため、iPhone を手に取らずに
    WebKit 固有の問題へ早期に気づける
- 欠点:
  - 開発者が macOS Safari を日常的に使っておらず、確認のたびに起動する手間が生じる
  - macOS Safari で再現しない iOS 固有の挙動も多い
    （ホーム画面追加した PWA の扱い、バイブレーションの有無、画面ロック中の音声）
- 却下理由:
  **iPhone での確認を早期かつ継続的に行う方針を採る以上、中間の検証層は重複する。**
  手間に見合う効果が得られない

### 案 B: Chrome + iPhone の 2 段階 — 採用

- 利点:
  - 手順が単純で、開発者の実際の利用環境と一致する
  - 確認の心理的コストが低く、結果として確認頻度が上がる
- 欠点:
  - WebKit の検証点が iPhone のみになる
- 採用理由: 開発者が macOS Safari を使用しておらず、
  かつ iPhone での早期確認を行う方針であるため、実態に即している

## 結果と影響

### 良い影響

- 確認手順が 2 環境に単純化され、開発のテンポが上がる
- 普段使わないブラウザを起動する負担がなくなり、確認が習慣として続きやすい

### 受け入れるトレードオフ

**iPhone が WebKit の唯一の検証点になる。**

中間の早期警告層を失うため、iPhone での確認を先送りすると、
iOS 固有の問題が一切検出されないまま実装が進む。
この方針は「iPhone で頻繁に確認すること」を前提として初めて成立する。

前提を担保するため、以下を必須とする。

- **#6 GitHub Pages のデプロイを M1 の中で優先する。**
  画面が未完成の段階でも、早期に iPhone のホーム画面へ追加できる状態を作る
- **#2 で Vite 開発サーバを LAN 公開する（`--host`）。**
  同じ Wi-Fi 上の iPhone から、デプロイを待たずに開発中の画面を確認できるようにする
- 以下の Issue は **iPhone で確認するまで完了としない**
  - #26 タイマー終了音（音声の自動再生制限）
  - #27 バイブレーション（非対応環境のフォールバック）
  - #40 PWA 化（ホーム画面追加とストレージ保持）
  - #43 ホーム画面への追加導線

### Android を未検証とすることのリスクは低い

Android 実機を持たないため Android Chrome は未検証となるが、リスクは小さい。

**Android Chrome は iOS Safari より制約が緩い環境だからである。**

| 制約 | iOS Safari | Android Chrome |
| --- | --- | --- |
| ストレージの自動削除 | あり | なし |
| `navigator.vibrate()` | 非対応 | 対応 |
| 音声の自動再生制限 | 厳しい | 緩い |

最も厳しい iOS Safari を基準に設計する以上、Android では自然に動作する可能性が高い。
逆であれば（Android を基準に作って iOS で確認しない）危険だが、本方針はそうなっていない。

有料の実機テストサービス（BrowserStack 等）は「完全無料」制約に反するため使用しない。
Android 固有の不具合が報告された時点で、改めて対応を検討する。

### デバッグ手段

iPhone 上の問題は、Mac の Safari Web Inspector で調査できる。

1. iPhone: 設定 > Safari > 詳細 > Web インスペクタ をオン
2. iPhone を Mac に USB 接続
3. Mac の Safari: 開発メニューから対象の iPhone を選ぶ

**macOS Safari を「確認環境」としては使わないが、「デバッグ道具」としては使う。**
この用途では Safari の起動が必要になるが、問題が起きたときだけでよい。
なお、この手段は Mac があって初めて成立する（追加費用は発生しない）。

## 備考

将来 Android 実機が利用可能になった場合は、本 ADR を `Superseded` とせず、
確認対象に追加する旨の ADR を起票すること。
