# ADR-0016: 合成した終了音は `<audio>` 要素で鳴らす

- **ステータス**: Accepted
- **日付**: 2026-08-18
- **関連**: ADR-0013, ADR-0007, ADR-0001
- **関連 Issue**: #85, #46

## コンテキスト

ADR-0013 で終了音を Web Audio API による合成と決め、
iOS の自動再生制限に対して「開始タップ時に AudioContext を unlock する」手当てを入れた。

**実機（iPhone）で確認したところ、25 分経過時に音が鳴らなかった**（#85）。
デスクトップ Chrome では鳴っている。ADR-0007 が警告していた
「Chrome で動いた」を「iPhone で動く」の保証にしてはいけない、という事例そのものである。

unlock の手当ては自動再生制限に対しては正しい。しかし iOS には**別の制約**があり、
そちらに対しては何の対策も入っていなかった。

### 制約 1: 消音スイッチは Web Audio だけを消す

iOS では音の出口が 2 系統ある。

| 経路 | 消音スイッチ（マナーモード） |
| --- | --- |
| Web Audio API の `destination` | **消える** |
| `<audio>` / `<video>` 要素の再生 | 消えない |

Safari で動画を見ると消音中でも音が出るのは後者だからである。
現状の実装は前者に直結しており、**本体側面のスイッチひとつで完全に無音になる。**

macOS の Chrome にこの区別は存在しない。この制約はデスクトップでは一切再現しない。

### 制約 2: AudioContext は背面に回ると止まる

iOS はページが背面に回ると AudioContext を止める。
25 分の途中で他のアプリを見れば、完了時点で `suspended` あるいは
WebKit 固有の `interrupted` になっている。

現状の `playChime()` は `resume()` の完了を待たずに音を組み立てており、
**再開に失敗しても分からない**（`catch` が空）。

### 制約 3: 音は完了通知の唯一の手段である

ADR-0001 でバイブレーションを任意機能に格下げした（iOS Safari は
`navigator.vibrate()` 非対応）。**iPhone では音が鳴らなければ何も起きない。**
仕様書 14 章の完成条件「終了時に音またはバイブレーションで知らせる」が満たせない。

## 決定

**音の合成方法は変えない。出口だけ `<audio>` 要素に変える。**

ADR-0013 の「Web Audio API で合成する / 音声ファイルを持たない」は維持する。
変えるのは、合成した音がスピーカーに届くまでの経路である。

1. `OfflineAudioContext` で終了音を**その場でレンダリングし、WAV に組み立てる**
2. Blob URL を `HTMLAudioElement` に渡す
3. **開始タップのうちに一度 `play()` して即座に止め、再生を許可させる**
4. 25 分後は、その要素を頭出しして `play()` するだけ

音声ファイルはリポジトリにも配信物にも増えない。生成は起動後のメモリ上で完結する。

**あわせて、終了音の試聴ボタンを置く。**

## 検討した選択肢

### 消音スイッチ対策

#### 案 A: 合成結果を WAV にして `<audio>` で鳴らす — 採用

- 利点:
  - **消音スイッチで消えない**
  - **25 分後に AudioContext の状態へ依存しない。** 制約 1 と制約 2 を一度に外せる
  - 音の内容はコードのままなので、ADR-0013 の調整しやすさが保たれる
- 欠点:
  - WAV の組み立てを自前で書く（ヘッダ 44 バイト + 16bit PCM）
  - 2 秒ぶんの PCM をメモリに置く（数百 KB）
- 採用理由: **鳴らない原因を 2 つまとめて外せる唯一の案。**
  WAV の組み立ては仕様が枯れており、書き切りで済む

#### 案 B: 無音の `<audio>` を先に鳴らし、音声セッションの種別を変える

ページ内で一度でも `<audio>` を再生すると、以降の Web Audio も
消音スイッチの影響を受けなくなる、という挙動を利用する案。

- 利点: 変更が小さい。合成の経路をそのまま使える
- 欠点:
  - **仕様として保証された挙動ではない。** WebKit の実装詳細に寄りかかる
  - 制約 2（背面で AudioContext が止まる）は解決しない
- 却下理由: 検証に 25 分かかる問題に対して、**確からしさで劣る案を選ぶ理由がない**

#### 案 C: 音声ファイルを同梱し、`<audio>` で鳴らす

- 却下理由: ADR-0013 で却下した理由がそのまま残っている。
  ライセンスの確認と追跡が必要になり、「完全無料」の制約（ADR-0001）に触れる。
  **案 A なら、ファイルを持たずに `<audio>` の利点だけ得られる**

### AudioContext を使い続けるか

`<audio>` が使えない環境のために、**Web Audio の経路は残して後段に置く。**

順に試し、鳴らせた時点で終わる。

1. 用意済みの `<audio>` を鳴らす
2. 失敗したら Web Audio で直接鳴らす（`resume()` の完了を待ってから組み立てる）

デスクトップ Chrome では 1 で鳴る。1 が使えない環境でも 2 で鳴る。

### 試聴ボタンを置くか

**置く。** これは音色の好みの問題ではなく、**確認可能性の問題**である。

現状、音を確かめる手段は「25 分待つ」しかない。
ADR-0013 は「音を聴けないため最終的な良し悪しは開発者の判断に委ねる」と書いたが、
**その判断を下す手段を用意していなかった。**

- 原因の切り分けに 25 分かかる
- 音色の調整（ADR-0013 が想定した作業）にも毎回 25 分かかる
- 消音スイッチが原因だった場合、ユーザーはそれに気づく機会がない

置き場所はタイマー画面の音のオン / オフの隣とする。
**そこが「音が鳴るか気になる」場所だから。**
仕様書 13 章の「静か」を損なわないよう、文字の小さな補助的な扱いにする。

### 鳴らなかったことを画面に出すか

**出さない。**

仕様書 13 章のトーンに反するうえ、鳴らない理由の大半（消音スイッチ）は
アプリからは判別できない。**確かめられないことを断定して伝えてはいけない。**

代わりに、試聴ボタンの近くに消音スイッチのことを一行添える。
音が鳴らない人が自分で確かめられれば足りる。

## 結果と影響

### 良い影響

- **消音スイッチが入っていても終了音が鳴る**
- 背面に回っていた場合でも、AudioContext の状態に左右されずに鳴る
- 音の確認が 25 分から 1 秒になる。音色の調整も現実的になった

### 受け入れるトレードオフ

**WAV の組み立てコードを持つことになる。**
音の長さを変えるとメモリ使用量も変わるが、2 秒程度である限り問題にならない。

**レンダリングは非同期で、開始タップ直後には間に合わないことがある。**
25 分の猶予があるため実害はない。試聴ボタンは、まだ用意できていなければ
Web Audio で直接鳴らす。

### 残るリスク

**画面ロック中に 25 分を迎えた場合は、依然として鳴らない。**

iOS はロック中に JS を凍結するため、**完了の検知自体が起きない。**
これは出口の問題ではなく、ADR-0013 のリスクとして記載済みの挙動であり、
本 ADR では解決しない。

緩和策は ADR-0013 のとおり、**画面に戻った時点で完了画面になっていること**。
根本対応（Notification API、あるいは 25 分後の音を事前に予約する方式）は
MVP 対象外とし、実機で「ロック中に鳴らないことが問題だ」と判断されてから起票する。

## 備考

**この修正が効いたかどうかは iPhone でしか確認できない**（ADR-0007）。
ヘッドレス Chrome には音声出力そのものがない。
自動テストで守るのは「経路の選択順」と「失敗しても例外を投げないこと」までとする。
