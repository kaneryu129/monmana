# ADR-0003: Issue 駆動開発と ADR の運用方針

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連**: docs/adr/README.md

## コンテキスト

モンまなの開発は、開発者と AI エージェント（Claude Code）の協働で進める。
この体制には固有の課題がある。

- AI が行った設計判断の根拠が残らず、後から検証できない
- 作業単位が曖昧だと、AI が一度に広範囲を変更し、レビューが困難になる
- 何をやったか・なぜそうしたかが会話ログの中にしか無く、リポジトリに残らない

参考にした記事は以下の 2 本。

- [GitHub Issue 駆動開発フロー (Qiita)](https://qiita.com/NaaaRiii/items/2e302283f96d2b0ee501)
  — 個人開発でも Issue を起点にすると衝突が少なく振り返り可能性が高い、という主張
- [ADR 導入事例 (Zenn)](https://zenn.dev/maman/articles/f91a52bc06024d)
  — 50 人弱のチームで属人化を解消した実例。ステータス遷移と「承認後は新規 ADR で置き換える」運用

いずれの記事も AI エージェントとの組み合わせには触れていないため、その部分は本 ADR で定める。

## 決定

**Issue 駆動開発を採用し、設計判断は ADR に記録する。**

### Issue の運用

1. 実装着手前に必ず Issue を作成する
2. Issue 番号を含むブランチを切る
   - `feature/12-timer-countdown`
   - `fix/23-streak-boundary`
   - `docs/31-adr-storage`
3. コミットメッセージに Issue 番号を含める
4. PR 本文に `Closes #12` を書く
5. マージ後、ローカル・リモート両方のブランチを削除する

### Issue の粒度

**細かく切る。** 1 Issue = 1 PR = 半日以内で終わる単位を目安とする。

モンまなは小規模なサービスであり、章単位（タイマー、成長ルール、植物ビュー）で切ると
1 Issue が大きくなりすぎる。AI エージェントに広範囲を一度に変更させると、
差分が読めなくなりレビューが形骸化する。これを防ぐために細分化する。

具体的には、以下のように分離する。

- ドメインロジックと UI は別 Issue にする
- 「タイマーのカウントダウン」と「タイマーの音」と「タイマーのバイブレーション」は別 Issue
- モンステラの描画は、レベル帯ごとに別 Issue

### ADR の運用

`docs/adr/README.md` に定めたルールに従う。要点は以下。

- 置き場所は `docs/adr/NNNN-kebab-case-title.md`
- ステータスは `Proposed` / `Accepted` / `Superseded by ADR-NNNN` の 3 つのみ
- **Accepted な ADR は書き換えず、新しい ADR で置き換える**（誤字修正は例外）
- 全 Issue には書かない。「後から理由を聞かれて困るもの」に限る

### AI エージェントに課す規約

これが本 ADR の中核であり、参考記事に無い部分である。

1. **設計判断を伴う実装の前に、ADR を書く。**
   実装してから事後的に理由を書くのではなく、判断時点で記録する
2. **却下した選択肢とその理由を必ず残す。**
   採用理由だけでは、後から「他は検討したのか」が分からない
3. **仕様書と異なる実装をする場合は、必ず ADR を書く。**
   技術的制約による妥協を、黙って実装に埋め込まない
4. **判断が開発者の制約に依存する場合、その制約を ADR に明記する。**
   例: ADR-0001 は「完全無料」制約に完全に依存しており、制約が変われば結論も変わる

## 検討した選択肢

### 案 A: Issue 駆動 + ADR — 採用

- 利点: 作業単位と判断根拠の両方がリポジトリに残る。AI の判断が検証可能になる
- 欠点: Issue 作成と ADR 執筆のオーバーヘッド
- 採用理由: AI 協働では判断の追跡可能性が特に重要。オーバーヘッドは粒度の線引きで抑制できる

### 案 B: Issue のみ（ADR なし）

- 利点: 手間が最小
- 欠点: 「なぜその技術を選んだか」が Issue のコメントに散逸する
- 却下理由: 開発者から ADR を残す明確な要望があった

### 案 C: 参考記事の運用をそのまま採用

- 欠点: Zenn の記事は 50 人弱のチーム向けで、`Draft → Proposed → Approved/Rejected` の
  4 段階と定例レビュー（10〜15 分）を前提にしている。個人開発では承認会が存在せず、
  ステータスが機能しない
- 却下理由: **重すぎて ADR が書かれなくなる**のが個人開発における典型的な失敗であるため、
  ステータスを 3 つに削り、承認プロセスを外した。
  ただし「Accepted 後は書き換えず新規 ADR で置換」という履歴保護の原則は残した

## 結果と影響

### 良い影響

- 実装の背景が Issue と ADR に残り、数か月後の自分が経緯を辿れる
- AI の設計判断が事後検証可能になる
- 細かい Issue により PR の差分が小さくなり、レビューが実質的に機能する

### 受け入れるトレードオフ

- Issue 作成のオーバーヘッドが発生する。ただし `gh issue create` で軽減する
- Issue 数が多くなる（MVP で 30 件程度）。ラベルとマイルストーンで整理する

## 備考

ADR を書く粒度の線引きは運用しながら調整する。
「ADR が多すぎて読まれない」「少なすぎて judgement が追えない」のどちらかに傾いたら、
`docs/adr/README.md` の基準を見直す。
なお、この見直しは README の運用ルール変更であり、既存 ADR の書き換えではない。
