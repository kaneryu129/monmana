# ADR-0004: 技術スタックは Vite + React + TypeScript とする

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連**: ADR-0001, ADR-0002, ADR-0005

## コンテキスト

ADR-0001 で Web (PWA) を採用した。その上で具体的なフレームワークとビルドツールを決める。

前提となる制約と要件は以下。

- 「完全無料」制約（ADR-0001）
- バックエンドを持たない（ADR-0002）。サーバーサイドレンダリングの必要がない
- モンステラの成長表現にアニメーションが必要（仕様書 7 章、8 章）
- ドメインロジックを UI から独立させる方針（ADR-0001 備考）

## 決定

**Vite + React + TypeScript を採用する。**

| 領域 | 採用技術 | 備考 |
| --- | --- | --- |
| ビルドツール | Vite | |
| UI ライブラリ | React | |
| 言語 | TypeScript | `strict: true` |
| ルーティング | React Router | 画面遷移は仕様書 4 章の 5 画面 |
| 状態管理 | React 標準（Context + useReducer） | 外部ライブラリを入れない |
| スタイリング | CSS Modules + CSS 変数 | デザイントークンを CSS 変数で定義 |
| テスト | Vitest | ドメインロジックの単体テスト用 |
| モンステラ描画 | インライン SVG + CSS アニメーション | |

## 検討した選択肢

### ビルドツール / フレームワーク

#### 案 A: Vite (SPA) — 採用

- 利点: 設定が軽い。開発サーバが速い。静的ファイルを吐くだけなので GitHub Pages と相性が良い
- 欠点: SSR や画像最適化などの機能は自前
- 採用理由: バックエンドが無く SEO 要件も無いため、SPA で必要十分

#### 案 B: Next.js

- 利点: 機能が豊富。ルーティングが規約ベース
- 欠点: SSR / API Routes / ISR など、本プロジェクトで使わない機能が大半。
  静的エクスポートすれば GitHub Pages に載るが、そのために制約を意識する手間が生じる。
  Vercel への依存を招きやすい
- 却下理由: **バックエンドを持たない決定（ADR-0002）により、Next.js の主要な利点が消える。**
  過剰な選択

#### 案 C: フレームワークなし（素の TypeScript + DOM 操作）

- 利点: 依存ゼロ。バンドルが最小
- 欠点: 5 画面の状態遷移とモンステラの段階的描画を手書きの DOM 操作で管理するのは、
  規模に対して割に合わない
- 却下理由: 開発効率が悪く、MVP 完成が遅れる

### 状態管理

#### 案 A: React 標準（Context + useReducer）— 採用

- 利点: 依存が増えない。学習コストなし
- 欠点: 大規模化すると再レンダリングの最適化が手間
- 採用理由: **扱う状態が小さい。** 実質「成長状態」と「進行中のタイマー」の 2 つだけ。
  外部ライブラリを入れる規模ではない

#### 案 B: Zustand / Jotai など

- 却下理由: 現時点の状態の少なさに対して過剰。必要になった時点で導入すればよく、
  先回りして依存を増やす理由がない

### スタイリング

#### 案 A: CSS Modules + CSS 変数 — 採用

- 利点: 追加の依存やビルド設定が要らない（Vite が標準対応）。
  仕様書 13 章の配色（白・淡いベージュ・深い緑・斑の淡い黄緑）を CSS 変数として
  一箇所に定義でき、成長段階に応じた配色変化も変数の差し替えで表現できる
- 採用理由: デザイントークンの一元管理という要件に素直に対応する

#### 案 B: Tailwind CSS

- 欠点: 設定が増える。仕様書 13 章の「静か」「余白が多い」という繊細なトーンは、
  ユーティリティクラスの組み合わせよりも、意味のある名前を付けた CSS 変数で
  管理したほうが意図が残る
- 却下理由: 本プロジェクトの世界観の作り込みには、デザイントークンを明示的に
  定義するアプローチのほうが合う

### アニメーション

#### 案 A: CSS アニメーション + SVG — 採用

- 利点: 依存ゼロ。仕様書 7 章の演出（葉が少し揺れる、水滴が落ちる、新芽が伸びる）は
  いずれも CSS transition / keyframes で表現できる範囲
- 採用理由: 仕様書 7 章が「毎回派手に演出しすぎない」「短く控えめ」と明記しており、
  高度なアニメーションライブラリを必要とする要件が無い

#### 案 B: Framer Motion

- 却下理由: 現時点の演出要件に対して過剰。レベルアップ演出（仕様書 7 章）が
  CSS では表現しきれないと判明した時点で、改めて導入を検討する

## 結果と影響

### 良い影響

- 依存ライブラリが少なく、ビルドが軽い。無料枠のビルド時間を圧迫しない
- ドメインロジックを純粋な TypeScript として書けるため、ADR-0001 で述べた
  React Native への移行時にそのまま再利用できる
- CSS 変数によるデザイントークンの一元管理で、仕様書 13 章のトーンを一貫させやすい

### 受け入れるトレードオフ

- SSR が無いため初回ロードで白画面の時間が生じる。
  ただしローカル完結のアプリであり、実用上の問題は小さい
- 状態管理を標準機能で行うため、状態が増えたら見直しが必要になる

## 備考

各ライブラリの追加は、必要が生じた時点で個別に判断する。
特に状態管理ライブラリとアニメーションライブラリは、
「今は要らない」という判断であって「永久に使わない」ではない。
導入する場合は本 ADR を `Superseded` とせず、追加の ADR を起票して差分を記録する。
