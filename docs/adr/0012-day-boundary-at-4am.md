# ADR-0012: 一日の境界を午前 4 時とする

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連 Issue**: #8, #12

## コンテキスト

仕様書 11 章は連続学習日数をこう定めている。

> その日に 1 分以上の学習記録があれば、連続学習日数を継続する

「その日」がいつからいつまでかは書かれていない。
連続日数の算出（#12）と、セッションの保存（#8）の両方がこの定義に依存するため、
先に決める必要がある。

想定ユーザーは「資格、語学、受験、プログラミングなどを学ぶ人」（仕様書 1 章）であり、
**深夜に勉強する人が一定数いる**と考えられる。

深夜 0 時を境界にすると、次の問題が起きる。

- 23:50 に始めて 0:15 に終えた学習が、2 日にまたがって扱われる
- 毎晩 1 時に勉強する人は、日付上は毎日学習しているのに
  「今日はまだ学習していない」状態の時間が長い
- 0 時をまたいだ瞬間に「連続記録が途切れる」可能性がある

これは仕様書 11 章の思想と正面から衝突する。

> 連続記録が途切れても、植物のレベル・見た目・累計成長ポイントは失われない
> 再開時は責めずに迎える

**技術的な都合で、休んでいない人の連続記録を切ってはいけない。**

## 決定

**一日の境界を午前 4 時とする。**

午前 0 時〜3 時 59 分の学習は、前日ぶんとして数える。

```ts
export const DAY_BOUNDARY_HOUR = 4
```

判定は端末のローカル時刻で行う。UTC は使わない。
ユーザーが感じる「その日」は手元の時計に従うため。

## 検討した選択肢

### 案 A: 午前 4 時を境界とする — 採用

- 利点:
  - **深夜の学習が前日ぶんとして数えられ、連続記録が不当に途切れない**
  - 生活実感に近い。「寝る前の勉強」は前日の行動として認識される
  - 家計簿アプリや勤怠管理など、同種の扱いをする例が多い
- 欠点:
  - 深夜 3 時に学習して「今日」と表示されないことに違和感を持つ人がいる可能性
  - 実装で日付を扱うたびにこの境界を意識する必要がある
- 採用理由: 仕様書 11 章の「責めない」という思想を、境界の設計で守る

### 案 B: 深夜 0 時を境界とする

- 利点: 実装が単純。暦どおりで説明が要らない
- 欠点: 上記のとおり、深夜に勉強する人の連続記録が途切れやすい
- 却下理由:
  **単純さのために体験を犠牲にしている。**
  連続日数はこのサービスで唯一「途切れる」値であり、
  そこを技術的都合で不利にするのは筋が悪い

### 案 C: ユーザーが境界を設定できるようにする

- 利点: 生活リズムに合わせられる
- 欠点: 設定項目が増える。MVP は設定を最小限にする方針
- 却下理由: MVP の範囲外。まず 4 時で運用し、要望が出たら検討する

## 結果と影響

### 良い影響

- 深夜まで勉強するユーザーの連続記録が、日付の変更で途切れなくなる
- 「今日の学習時間」が、寝るまで同じ日のものとして積み上がる

### 受け入れるトレードオフ

**午前 0 時〜4 時の表示が暦の日付とずれる。**

深夜 2 時に開いたとき、ホーム画面の日付は前日を指す。
これが混乱を招く場合は、表示上の工夫（「8月15日（金）の夜」のような表記）を検討する。
ただし MVP では単純に前日として扱う。

### 実装上の制約

- **セッションの `dateKey` は保存時に確定させる。**
  `startedAt` から毎回導出すると、端末のタイムゾーンが変わったときに
  過去の記録の所属日が動いてしまう。積み上げた記録は動かさない
- 日付を扱う処理は `src/domain/dateKey.ts` に集約し、
  境界の判断を散らばらせない
- **日数の差はミリ秒の割り算で求めない。**
  夏時間のある地域では 1 日が 23 時間や 25 時間になるため、
  正午に揃えてから差を取る

## 備考

境界時刻は `toDateKey(at, boundaryHour)` の第 2 引数で差し替えられるようにしてある。
将来ユーザー設定として開放する場合も、この関数の呼び出し側を変えるだけで済む。
