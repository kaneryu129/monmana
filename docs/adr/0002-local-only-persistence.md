# ADR-0002: データは端末内ローカルのみに保存する

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連**: ADR-0001

## コンテキスト

MVP 仕様書 12 章で、学習セッションとユーザーの成長状態を保持することが定められている。
また 14 章の完成条件に「次回アプリを開いたときにも、学習記録とモンステラの成長状態が
保持されている」がある。

一方で 2 章では、以下が MVP 対象外と明記されている。

- ログイン、アカウント作成
- 複数端末での同期

さらに ADR-0001 で確定した「完全無料」制約が、バックエンド構築の判断にも影響する。

## 決定

**学習データは端末内のローカルストレージのみに保存し、バックエンドを持たない。**

- 保存先は **IndexedDB** を使用する
- サーバー、API、データベースは MVP では構築しない
- データのスキーマにバージョン番号を持たせ、将来のマイグレーションに備える

## 検討した選択肢

### 案 A: 端末内ローカル保存のみ — 採用

- 利点: 費用ゼロ。バックエンド実装が不要で MVP が最速。個人の学習記録が外部に出ない
- 欠点: 端末間で同期できない。端末故障やストレージ消去でデータが失われる
- 採用理由: 仕様書が同期を対象外としており、無料制約とも合致する

### 案 B: 簡易バックエンドを最初から用意する

- 利点: 将来の複数端末同期・機能拡張への移行が容易
- 欠点: 無料枠のある BaaS でも、無料枠超過や sunset のリスクが残り「完全無料」を保証できない。
  認証が必要になり、仕様書が対象外としたログイン機能を実装する羽目になる
- 却下理由: MVP 範囲外の機能を呼び込み、費用制約の保証も難しい

### 保存先の選択（案 A 採用後の詳細）

#### localStorage

- 利点: API が単純。同期的に読み書きできる
- 欠点: 容量上限が約 5MB。同期 API のためメインスレッドをブロックする。
  構造化データを扱うには JSON の手動シリアライズが必要
- 却下理由: 学習セッションは毎日蓄積される構造化データであり、
  件数の増加に対して JSON 全体の読み書きは筋が悪い

#### IndexedDB — 採用

- 利点: 容量が大きい。構造化データをそのまま扱える。インデックスで日付範囲の検索ができる
- 欠点: 生の API が冗長。非同期
- 採用理由: 仕様書 12 章のデータ構造（セッションの集合＋成長状態）と素直に対応する。
  「今日の学習時間」「連続学習日数」の算出で日付による絞り込みが必要になるため、
  インデックスが張れる利点が効く。API の冗長さは薄いラッパで吸収する

## 結果と影響

### 良い影響

- バックエンド起因の障害・費用・運用が一切発生しない
- オフラインでも完全に動作する。学習中にネットワークを必要としない
- 学習記録という個人的なデータが端末外に出ない

### 受け入れるトレードオフ

- 機種変更でデータが引き継がれない
- 複数端末で同じモンステラを育てられない

### 残るリスクと緩和策

**リスク: ストレージ消去によるデータ消失**

ADR-0001 に記載のとおり、iOS Safari の ITP は 7 日間の無操作でストレージを削除する。
また、ユーザーがブラウザのデータ消去を行った場合も失われる。

積み上げた学習記録の消失は、このサービスの価値そのものの喪失を意味する。
「モンステラは枯れない」という仕様書 10 章の約束が、技術的理由で破られることになる。

緩和策:
- **エクスポート / インポート機能を MVP に含める**（当初の仕様書には無い機能だが、
  上記の理由により必要と判断した）
- ホーム画面への追加を促し、ITP の削除対象から外す

## 備考

将来クラウド同期を実装する場合、本 ADR を `Superseded` とし、
ローカルデータの移行方針を含む新しい ADR を起票すること。
その移行を容易にするため、**ストレージアクセスは抽象化層を挟み、
ドメインロジックが IndexedDB に直接依存しないようにする。**
