# Architecture Decision Records (ADR)

このディレクトリには、モンまなの設計判断とその理由を記録します。

## なぜ書くのか

コードを読めば「何をしているか」は分かりますが、「なぜそうしたのか」は残りません。
後から自分自身が「ここ、どうしてこうなってるんだっけ」と迷ったときに、
当時の制約と検討過程を辿れるようにするのが目的です。

特にこのプロジェクトでは、AI エージェント（Claude Code）が設計判断を行う場面があります。
その判断根拠を残さないと、判断がブラックボックス化します。ADR はその歯止めです。

## ファイル名

```
docs/adr/NNNN-kebab-case-title.md
```

`NNNN` は 0001 から始まる連番。欠番は作らず、採番したら Rejected になっても番号は再利用しません。

## ステータス

個人開発のため、承認会のような重い運用はしません。3 つだけ使います。

| ステータス | 意味 |
| --- | --- |
| `Proposed` | 提案済み。まだ実装に反映していない、または判断を保留している |
| `Accepted` | 採用済み。現在の設計はこれに従う |
| `Superseded by ADR-NNNN` | 別の ADR に置き換えられた。内容は残す |

## 運用ルール

1. **Accepted になった ADR は書き換えない。**
   決定が変わったときは、新しい ADR を起票して古い方を `Superseded` にします。
   誤字脱字とリンク切れの修正だけは例外です。
   これは「いつ何を考えて決めたか」の履歴そのものを守るためのルールです。

2. **すべての Issue に ADR を書かない。**
   書くのは「後から理由を聞かれて答えられないと困るもの」に限ります。

   | 書く | 書かない |
   | --- | --- |
   | プラットフォーム・技術スタックの選定 | 変数名やコンポーネント名 |
   | データの持ち方、永続化の方式 | CSS の微調整 |
   | ドメインロジックの置き場所 | 誤字修正、リファクタ |
   | 外部制約への対処方針 | 仕様書にそのまま書いてあることの実装 |
   | 仕様書の記述を変更・妥協した判断 | |

3. **Issue と相互リンクする。**
   ADR には関連 Issue 番号を、Issue には関連 ADR 番号を書きます。
   どちらからでも辿れる状態にしておきます。

4. **仕様書と食い違う判断をしたら必ず ADR を書く。**
   MVP 仕様書は現時点の理想です。技術的制約で仕様どおりにできない場合、
   黙って実装を変えるのではなく、何をなぜ諦めたかを ADR に残します。
