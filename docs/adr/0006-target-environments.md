# ADR-0006: 対応環境はデスクトップ Chrome とモバイル（iOS / Android）の両方とする

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連**: ADR-0001, ADR-0002, ADR-0005
- **関連 Issue**: #40, #43, #44, #46

## コンテキスト

ADR-0001 でプラットフォームを Web (PWA) と決めたが、
**どのブラウザ・デバイスを対象とするか**は未確定だった。

この範囲は以下を直接左右するため、明示的に決める必要がある。

- テストに必要な環境の数
- 一部機能（PWA 化、エクスポート / インポート）が必須かどうか
- iOS 固有の制約への対処が必要かどうか

開発者の開発環境は macOS + Chrome であり、
「開発中は PC の Chrome で動けばよいのではないか」という確認があった。

## 決定

**デスクトップ Chrome とモバイル（iOS Safari / Android Chrome）の両方を対象とする。**

| 環境 | 位置づけ |
| --- | --- |
| デスクトップ Chrome (macOS) | 開発とデバッグの主環境 |
| iOS Safari（ホーム画面追加） | 実利用の主環境。**制約が最も厳しく、設計の基準となる** |
| Android Chrome | 実利用の対象 |

開発は Chrome で高速に回し、**リリース前に実機で確認する**という二段構えを採る。

## 検討した選択肢

### 案 A: デスクトップ Chrome とモバイルの両方 — 採用

- 利点:
  - Web アプリのため、**追加の実装コストなしに両対応できる**。
    同一の URL・同一のコードベースで動作し、別ビルドも別コードも不要
  - 25 分タイマーで勉強する間、スマートフォンを机に置いて使う利用形態に対応できる。
    仕様書はこの使い方を前提としている（6 章の「バイブレーション」がその証左）
- 欠点: テスト環境が 3 つに増える。iOS 固有の制約への対処が必須になる
- 採用理由: 追加コストがほぼ無い一方、利用場面が大きく広がる

### 案 B: デスクトップ Chrome のみ

- 利点:
  - iOS Safari の制約（ストレージ削除、バイブレーション非対応、自動再生制限）を
    すべて無視できる
  - PWA 化（#40）とホーム画面追加の導線（#43）が不要になる
  - テストが 1 環境で済む
- 却下理由:
  **勉強中は PC を学習そのものに使っているか、あるいは机上のノートに向かっている。**
  タイマーを PC の画面上でしか確認できないのは、学習の妨げになる場面が多い。
  スマートフォンを傍らに置いて時間を計る形態のほうが、このサービスの利用実態に合う

### 案 C: モバイルのみ

- 利点: 対象を絞れる
- 却下理由: 開発とデバッグに Chrome DevTools を使うため、
  結局デスクトップでの動作は必要になる。絞る意味がない

## 結果と影響

### 良い影響

- ADR-0001 で「完全無料」制約により Web を選んだ結果、
  **マルチデバイス対応が追加コストなしで得られた**。
  ストア配信を選んでいた場合、iOS 実機での動作確認だけで年間 $99 が必要だった
- URL を共有するだけで、どの端末からでも試してもらえる

### 受け入れるトレードオフ

- 動作確認が 3 環境必要になる（Issue #46 の通し確認で担保する）
- iOS Safari を基準に設計する必要があり、最も制約の厳しい環境に合わせることになる

### 残るリスクと緩和策

**リスク: デスクトップ Chrome での確認を「完了」と誤認すること**

ADR-0001 / ADR-0002 に記録したリスクの大半は、**デスクトップ Chrome では再現しない。**

| 制約 | デスクトップ Chrome | iOS Safari |
| --- | --- | --- |
| 7 日間の無操作でストレージ削除 | 起きない | **起きる**（ホーム画面追加で回避） |
| `navigator.vibrate()` | 動作する | **非対応** |
| 音声の自動再生制限 | 緩い | **厳しい**（要 unlock） |

つまり「Chrome で動いた」は「iPhone で動く」の保証にならない。
最も危険な失敗モードが、主開発環境では一切表面化しない。

緩和策:
- 上記 3 点に関わる Issue（#26 終了音、#27 バイブレーション、#40 PWA 化、
  #43 ホーム画面追加）は、**実機で確認するまで完了としない**
- 早期に GitHub Pages へデプロイし（#6）、実機で触れる状態を作っておく。
  開発の終盤まで実機確認を先送りしない
- 開発サーバを LAN に公開し（Vite の `--host`）、
  デプロイせずにスマートフォンから開発中の画面を確認できるようにする

**補足: バックグラウンドでのタイマー精度は Chrome でも再現する**

Chrome も非アクティブタブの `setInterval` をスロットリングするため、
ADR-0001 のリスク 2（タイマー精度）はデスクトップで検証できる。
`Date.now()` 基準の実装が正しいかは、実機を待たずに確認してよい。

## 備考

エクスポート / インポート（#44）は、iOS のストレージ削除対策として ADR-0002 で
追加したものだが、**デスクトップのみの対象だったとしても価値は残る**。
ブラウザのデータ消去や PC の買い替えでデータが失われる点は Chrome でも同じであり、
バックエンドを持たない以上（ADR-0002）、復旧手段は他に存在しないため。
