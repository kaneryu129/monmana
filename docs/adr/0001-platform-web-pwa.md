# ADR-0001: プラットフォームは Web (PWA) とする

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連**: ADR-0004, ADR-0005

## コンテキスト

モンまな MVP を実装するにあたり、実行プラットフォームを決める必要があった。

MVP 仕様書のうち、プラットフォーム選定に影響する要件は以下の 3 点。

- 6 章: 25 分経過時に「穏やかな終了音と軽いバイブレーション」を行う
- 14 章: 「次回アプリを開いたときにも、学習記録とモンステラの成長状態が保持されている」
- 2 章: ログイン・複数端末同期は MVP 対象外

### 判断を保留した経緯

当初、開発者に選択肢（Web / React Native (Expo) / ネイティブ個別実装）を提示した際、
判断は保留となった。この時点での評価は以下のとおりで、決め手を欠いていた。

- Web は開発と配布が速いが、iOS Safari がバイブレーション API 非対応
- React Native は音・バイブレーションをネイティブ API でフル対応できる
- ネイティブ個別実装は MVP には過剰

この時点では **バイブレーション対応を重視して React Native を推奨**していた。

### 判断を確定させた制約

その後、開発者から「**完全無料でできることを重視する**」という制約が追加された。
これは既存の評価軸を上書きする強い制約であり、以下の事実により選択肢が一意に定まった。

| 配布経路 | 費用 |
| --- | --- |
| App Store | Apple Developer Program **年間 $99** |
| Google Play | Developer 登録 **初回 $25** |
| Web (PWA) | **$0**（公開リポジトリの GitHub Pages で無料ホスティング可能） |

React Native / ネイティブは、実装自体は無料でも**実機配布の時点で必ず課金が発生する**。
Expo Go による開発中の動作確認は無料だが、それは配布ではない。
したがって「完全無料」の制約下では、ストア配信を前提とする選択肢はすべて成立しない。

## 決定

**モンまなは Web アプリ (PWA) として実装する。**

- ブラウザで動作し、iOS / Android ではホーム画面に追加して使うことを想定する
- ストア配信は行わない
- 仕様書 6 章のバイブレーションは、**対応環境でのみ動作する任意機能**に格下げする（後述）

## 検討した選択肢

### 案 A: Web (PWA) — 採用

- 利点: 費用ゼロ。配布が URL のみで完結。開発イテレーションが最速。OS 審査なし
- 欠点: iOS でバイブレーション不可。ストレージ揮発リスク。バックグラウンド動作に制約
- 採用理由: 「完全無料」制約を満たす唯一の選択肢。欠点はいずれも緩和策が存在する

### 案 B: React Native (Expo)

- 利点: 音・バイブレーション・通知をネイティブ API でフル対応。単一コードベースで iOS/Android
- 欠点: 実機配布に **年間 $99 + $25** が必要。ビルド環境（Xcode / Android Studio）の準備が必要
- 却下理由: **「完全無料」制約に違反する。** 技術的優位性はあるが、制約が上位にある

### 案 C: ネイティブ個別実装 (Swift / Kotlin)

- 利点: 各 OS に最適化できる
- 欠点: 案 B の費用に加え、開発量が 2 倍
- 却下理由: 費用制約に違反し、かつ MVP の規模に対して過剰

## 結果と影響

### 良い影響

- 費用ゼロで MVP を完成・公開できる
- URL を共有するだけで他人に触ってもらえる。フィードバックの獲得が速い
- リリースにストア審査の待ち時間がない

### 受け入れるトレードオフ

**仕様書 6 章の「バイブレーション」を必須要件から外す。**
これは仕様書の記述を実装側の都合で変更する判断であるため、明示的に記録する。

- `navigator.vibrate()` は **iOS Safari が非対応**（Android Chrome は対応）
- 対応環境でのみ振動させ、非対応環境では**音のみで完了を知らせる**（graceful degradation）
- 「軽いバイブレーション」は体験の中核ではなく補助的な通知であり、
  音が鳴れば仕様書 14 章の完成条件「終了時に音**または**バイブレーションで知らせる」は満たせる

### 残るリスクと緩和策

**リスク 1: iOS Safari のストレージ消去**

Safari は ITP により、7 日間サイトを操作しないと localStorage / IndexedDB を含む
スクリプト書き込み可能ストレージを削除する。これは仕様書 14 章の
「次回アプリを開いたときにも成長状態が保持されている」を直接脅かす。

緩和策:
- **ホーム画面に追加された PWA はこの削除の対象外**。ホーム画面追加を明確に促す導線を用意する
- 学習データの **エクスポート / インポート機能**を用意し、消失時に復旧できる逃げ道を作る
- 毎日使うアプリという性質上、7 日間の完全な無操作は起きにくい（ただし「休んでもよい」という
  仕様書 11 章の思想と衝突するため、上記 2 つの緩和策は必須とする）

**リスク 2: バックグラウンドでのタイマー精度**

タブが非アクティブになると `setInterval` はスロットリングされ、
ティックを数える実装では 25 分が正確に計測できない。

緩和策:
- 開始時刻を `Date.now()` で記録し、**経過時間は常に現在時刻との差分から算出する**。
  ティックは描画更新のトリガーにのみ使い、時間の真実の源にしない

**リスク 3: 画面ロック中に終了音が鳴らない可能性**

iOS では画面ロックやタブ離脱中に音声再生がブロックされることがある。

緩和策:
- 「25 分、勉強を始める」のタップを**ユーザージェスチャとして利用し、その時点で AudioContext を
  unlock** しておく（iOS の自動再生制限の回避に必須）
- 将来的には、ホーム画面追加済み PWA で使える Notification API（iOS 16.4+）を検討する。
  ただし MVP 対象外

## 備考

この決定は「完全無料」制約に完全に依存している。
将来、ストア配信の費用を許容する方針に変わった場合は、この ADR を見直し、
React Native への移行を検討する余地がある。その際は本 ADR を `Superseded` とし、
新しい ADR を起票すること。

なお、後述の ADR-0004 でフレームワークに React を選定しているため、
React Native への移行時にドメインロジック（純粋な TypeScript 部分）は再利用できる。
この再利用性を確保するため、**ドメインロジックは UI から独立させる**方針を採る。
