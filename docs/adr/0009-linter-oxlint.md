# ADR-0009: リンタは oxlint を使う

- **ステータス**: Accepted
- **日付**: 2026-08-15
- **関連**: ADR-0004
- **関連 Issue**: #2, #3

## コンテキスト

Issue #3 は「ESLint / Prettier を設定する」として起票していた。
ADR-0004 で技術スタックを決めた際、リンタは具体的に指定していなかった。

プロジェクト初期化（#2）で `npm create vite@latest --template react-ts` を実行したところ、
**Vite 9 のテンプレートは ESLint ではなく oxlint を同梱していた。**

生成された `.oxlintrc.json`:

```json
{
  "plugins": ["react", "typescript", "oxc"],
  "rules": {
    "react/rules-of-hooks": "error",
    "react/only-export-components": ["warn", { "allowConstantExport": true }]
  }
}
```

Issue #3 の前提が変わったため、どちらを使うか判断する必要が生じた。

## 決定

**oxlint をそのまま使う。ESLint へ差し替えない。**

## 検討した選択肢

### 案 A: oxlint をそのまま使う — 採用

- 利点:
  - **テンプレートの既定であり、追加設定が要らない。**
    既定の状態で `react/rules-of-hooks` が有効になっており、
    React で最も事故が起きやすい箇所は押さえられている
  - Rust 実装で高速。CI（#4）の実行時間を圧迫しない
  - 依存が少ない。ESLint は本体とプラグイン群で依存が増える
- 欠点:
  - ESLint に比べてルール数とプラグインの選択肢が少ない
  - 情報量が少なく、詰まったときに解決しづらい可能性がある
- 採用理由:
  **既定から外れるには理由が要る。** 現時点でその理由が無い。
  本プロジェクトは小規模で、必要なルールは既定でほぼ満たされている

### 案 B: ESLint に差し替える

- 利点: エコシステムが大きく、React 向けプラグインが成熟している
- 欠点: 設定ファイルと依存が増える。テンプレートの既定を意図的に壊すことになる
- 却下理由:
  現時点で oxlint に不足は見つかっていない。
  **必要が生じていない段階で依存を増やさない**という ADR-0004 の方針に反する

## 結果と影響

### 良い影響

- 初期設定の手間がゼロ。`npm run lint` がそのまま動く
- Lint の実行が速く、CI の待ち時間が短い

### 受け入れるトレードオフ

- ESLint 固有のプラグインが必要になった場合、そのルールは使えない
- ルールの追加や調整で情報が見つかりにくい場面があり得る

### Prettier について

**Prettier はまだ導入していない。** Issue #3 の残りとして扱う。

oxlint は整形ツールではないため、整形は別途必要になる。
導入時は本 ADR を `Superseded` とせず、Issue #3 の中で判断する。

## 備考

oxlint で表現できないルールが必要になり、それが実際に問題を起こした場合は、
本 ADR を `Superseded` として ESLint への移行 ADR を起票すること。
「なんとなく ESLint のほうが安心」では移行しない。**具体的に困った事例を根拠にする。**
