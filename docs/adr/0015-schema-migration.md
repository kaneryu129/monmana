# ADR-0015: スキーマ移行はデータ保持を最優先にし、消す操作を持たない

- **ステータス**: Accepted
- **日付**: 2026-08-17
- **関連**: ADR-0002, ADR-0014
- **関連 Issue**: #16, #42

## コンテキスト

ADR-0002 で「スキーマにバージョン番号を持たせ、将来のマイグレーションに備える」と決め、
**「マイグレーション失敗時の方針（データ保持を最優先にする設計）を ADR に記録すること」**
を宿題として残していた。本 ADR がその決定にあたる。

この判断が重い理由は、ADR-0002 の前提にある。

- バックエンドを持たない。データは端末内にしか存在しない
- したがって**スキーマ変更でデータを壊すと、復旧手段が一切ない**
- 「モンステラは枯れない」（仕様書 10 章）という約束が、技術的理由で破られる

さらに PWA 化（ADR-0014）により、**古い版のコードが端末に残る場合がある。**
Service Worker が更新される前に、新しい版で書かれたデータを古いコードが開く、
という順序が起こりうる。

## 決定

**移行はデータ保持を最優先にする。以下を原則とする。**

1. **前進のみ。** 移行関数は版を上げる方向にだけ書く。下げる移行は用意しない
2. **消さない。** ストアもレコードも、移行の中で削除しない。
   使わなくなった項目は残したまま無視する
3. **古いコードが新しいデータを開いたら、そのまま開く。**
   版を下げようとせず、既存の版で開いて読めるものを読む
4. **移行に失敗したら、書き込まずに退避する。**
   インメモリに切り替えてアプリは動かし、既存データには触らない

## 検討した選択肢

### 版が合わないときの扱い

#### 案 A: データ保持を最優先。読めなければ書き込まない — 採用

- 利点: **どの経路でも既存データを壊さない**
- 欠点: 古いコードでは新しい項目を扱えず、機能が一部欠ける可能性がある
- 採用理由: 復旧手段が無い以上、機能の欠落よりデータの消失のほうが害が大きい。
  古い版が残るのは一時的で、次の起動で新しい版に入れ替わる（ADR-0014 の自動更新）

#### 案 B: 版が合わなければ作り直す

- 利点: 実装が単純。状態が常に予測できる
- 欠点: **積み上げた学習記録が消える**
- 却下理由: このサービスの価値そのものを壊す。検討に値しない

#### 案 C: 版が合わなければアプリを止め、案内を出す

- 利点: 壊れたまま動くより安全
- 欠点: 学習を始めようとした人が何もできない
- 却下理由: 案 A で「読めるものを読む」ほうが、体験を止めずに済む。
  仕様書 13 章のトーンからも、行き止まりを見せたくない

### 移行前にバックアップを取るか

取らない。IndexedDB の中身を IndexedDB へ複製しても、
同じストレージが消えれば両方消える。意味のある保険にならない。

代わりに、**ユーザーが自分で持ち出せる経路（#42）を用意した**。
これが実効性のある唯一の保険である。

## 結果と影響

### 良い影響

- スキーマを変えるときに、データ消失の心配をせずに済む
- 古い版のコードが残っていても、記録が失われない

### 受け入れるトレードオフ

**使わなくなった項目が残り続ける。**
消さない方針のため、スキーマは肥大する方向にしか進まない。
学習記録は 1 件あたり数百バイトであり、実用上の問題は生じない。

**古いコードでは新しい項目が扱えない。**
一時的な状態であり、次の起動で解消する（ADR-0014）。

### 移行を書くときの決まり

```ts
// migrations.ts
export const migrations: Migration[] = [
  // 版 1 → 2 の例
  // { to: 2, run: (db, tx) => { /* ストアや索引を足すだけ */ } },
]
```

- `run` の中で `deleteObjectStore` と `deleteIndex` を使わない
- レコードを消す処理を書かない
- 既存レコードに項目を足す場合、**既存の値を上書きしない**

## 備考

移行を初めて書くときは、書き出したファイル（#42）を使って
「古い版のデータを取り込み、移行が走り、記録が残る」ことを実機で確認すること。
移行の検証はテストだけでは足りない。
